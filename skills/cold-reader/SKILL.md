# cold-reader（文脈を持たない読み手）

書き手は文脈を持っているので、文脈が無いと読めない箇所が見えない。
こうした箇所は、たいてい人のレビューで初めて見つかる。
この工程は、その役を「文脈を渡さないサブエージェント」に先にやらせる。

対象にする失敗は次の6つの型だけ。
どれも読み手の知識と本文のずれで起き、文単体の検査では拾えない。

例はすべて1つの架空の題材にそろえている。
Discord の「自宅サーバーのバックアップってどうしてます？ 消えたら詰むのが怖くて…」というスレッドで、
書き手が「NAS と外付けディスクで二重に取ってる」と書き、それに「保管庫は具体的にどこ？」と質問が来た。
その質問への返事を書いている。

| 型 | 名前 | 例 |
|---|---|---|
| 1 | 指すものが決まらない | 保管庫はNASです／同じフォルダ／残りの3つ |
| 2 | 呼び名の言い直し・その場の造語 | サーバーの外に置いた控え／サーバーの外 |
| 3 | 借りた言葉を定義せずに使う | 「詰むことへの対策」（何が起きると詰むのかが無い） |
| 4 | 誰も言っていないことの否定 | 台数ではなく |
| 5 | 結論の段落で前の段落を言い直す | 最後の段落まるごと（新しい点は1つだけ） |
| 6 | 主張の範囲がずれる | 「私の環境では」が無く、バックアップ一般の話に読める |

翻訳調・比喩の動詞・語尾の単調さは、読みやすさの書き直しの工程で見るので、ここでは扱わない。

## 位置

段落の組み立て → 文の規範 → 読みやすさの書き直し → 改行と空行（line-layout）→ **cold-reader** → 出す。
読みやすさの書き直しより後に置くのは、書き直しで主語や指示語が変わり、型1・型6が新しく生まれることがあるため。

## 手順

パスはこの SKILL.md があるディレクトリから見たもの。

### 1. 読み手を1行で決める

「誰が読むか」と「その人がすでに知っていること」を1行で書く。
分からないことも書く。

> 例: 質問した人。自宅サーバーを動かしていて、NAS・rsync・外付けディスクはだいたい知っている。書き手の機材構成・スクリプト・使っているバックアップのツールは知らない。
> 「自宅サーバーのバックアップってどうしてます？ 消えたら詰むのが怖くて…」というスレッドで、書き手の「NAS と外付けディスクで二重に取ってる」に「保管庫は具体的にどこ？」と質問した。

相手の質問・スレッドの題があれば原文のまま入れる。
型3（借りた言葉）と型4（誰も言っていない否定）は、読み手が何を言ったかが分からないと判定できない。

### 2. 自己点検（`references/self-check.md`）

6つの問いを自分で当てて、見つかったものを直す。
続けて機械検査を回す。

```bash
python3 scripts/restate_check.py draft.md
```

`LOW` が付いた段落は型5の疑い。
その段落で初めて言っていることを1つ挙げ、無ければ段落ごと削り、あればその1点を理由を述べている段落へ移す。
この検査は語の重なりしか見ないので、言い換えた要約は拾わない。

README のような、同じ用語を節ごとに使い回す参照用の文書では誤検知が多い。
そこでは LOW の段落を読み、新しい条件・理由・値があれば残す。

### 3. 冷えた読み手に読ませる

サブエージェントを**1体**起動する（`general-purpose`、`model: sonnet` で足りる）。
`references/reader-prompt.md` の指示に、手順1の読み手の1行と本文**だけ**を埋めて渡す。

渡さないもの: 会話の経緯、元にしたファイルやパス、書き手の意図、前の版、「どこを直したか」。
どれか1つでも渡すと、読み手は書き手の文脈で補って読み、型1〜3を見落とす。

読み手は「段落# / 引用 / 型 / なぜ困るか / 直し案」の表を返す。

### 4. 指摘を1件ずつ処理する

各指摘について、**直す**か、**直さない理由を書く**かのどちらか。
直さない理由には、それで問題ないと言える具体的な根拠を名指しする。

- 型1・2・3・6: 「読み手は〜を知っている（質問の〜という文から）」のように、読み手の知識の出どころを書く。
- 型4: 否定している主張を**誰が言ったか**を書く（「質問者がスレッドで『〜』と書いた」）。名指しできなければ否定を消す。
- 型5: その段落で初めて言っていることを引用する。

根拠を後から作って指摘を通さない。
たとえば「台数ではなく」を「読み手が思いそうな見方を正す否定」として残しても、誰もそう主張していなければ、人のレビューで消されるだけになる。
名指しできない理由は理由ではない。

読み手の直し案に本文に無い事実が含まれていたら、事実は書き手が確かめてから入れる。
読み手の推測をそのまま本文にしない。

### 5. 必要なら2回目

直した箇所が **4件以上**、または段落を削った・移したときは、直した版でもう一度だけ手順3を回す。
このときは新しい読み手を起動する（1回目の読み手を再利用しない）。
2回目で出た指摘は手順4で処理して終わる。
3回目は回さない。

### 6. 記録して見せる

本文と一緒に、指摘の一覧（直した／直さない理由）を短く付けて渡す。
人がレビューするとき、どこが冷えた読み手で見つかり、どこが見つからなかったかが分かるようにするため。

## スクリプトとテスト

- `scripts/restate_check.py` — 型5の機械検査。段落ごとに「前の段落で2回以上使われた語の割合（中心語の再利用率）」を出し、0.40 以上の段落に `LOW` を付ける。較正の値と既知の制限はファイル冒頭の docstring にある。
- `tests/test_restate_check.py` — 架空の題材の下書きで、要約になっている最後の段落が検出され、最終版の段落が検出されないことを確かめる。
  `python3 -m unittest discover -s tests`

## 評価

この工程の有り無しで2本ずつ下書きを書かせ、どちらの条件で書かれたかを伏せた判定役が6つの型の失敗を数えた。
工程が無い下書きは 4件・7件、有る下書きは 1件・0件だった。
